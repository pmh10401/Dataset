필수 계약

  • BackendAssessmentAntigravity, RuntimeAssessmentAntigravity, fixed_reference_rows_antigravity(), assess_runtime_antigravity(...)를 제공한다.
  • Numba cold 1회와 warm 반복 시간을 전송·동기화까지 포함해 기록한다. warm median과 IQR을 기록하고 repetitions는 양의 정수만 허용한다.
  • 동일 입력의 Numba 전체 결과 bytes가 반복마다 같아야 한다. 다르면 즉시 RuntimeError다.
  • 별도 공개 고정 fixture에서 Python과 Numba의 peak, presence, shift, rank, confirmation은 정확히 같고 raw/max 오차는 기본 1e-12 이하여야 한다. 실패하면 즉시 RuntimeError다.
  • backend manifest에는 정확히 numba와 mlx만 둔다. NumPy backend나 자동 fallback scorer는 만들지 않는다.
  • MLX는 Task 2와 같은 median/MAD, biased ACF lag 1..25, local peak lag 2..24, 작은 lag 동점, LOO raw, rank, strict confirmation을 계산한다. finite, exact discrete parity, raw 오차, 결정성, transfer/sync 포함 속도를 검사한다.
  • MLX가 없거나 float64를 보존하지 못하거나 parity·결정성·1.1× 중 하나라도 실패하면 eligible=false와 구체적인 fallback_reason을 남긴다. 오류 때문에 Numba 선택을 바꾸거나 NumPy로 계산하지 않는다.
  • Python, NumPy, Numba, llvmlite, MLX, mlx-metal 버전과 장치·플랫폼을 JSON manifest에 기록한다. 얻을 수 없는 값은 비밀정보 없이 null 또는 설명 문자열로 기록한다.
  • CLI는 공개 fixture assessment JSON만 지정 경로에 쓴다. 출력 JSON은 finite하고 정렬된 key·들여쓰기로 재현 가능해야 한다.

TDD 순서와 테스트

  1. production 파일보다 먼저 테스트를 만들고 missing-module RED를 실행 기록에 남긴다.
  2. 고정 fixture shape/dtype/C-contiguous/writeable=false와 외부 데이터 미사용을 검사한다.
  3. Numba가 Python 기준을 통과하고 전체 bytes가 결정적이며 선택 backend가 항상 numba인지 검사한다.
  4. backend key가 정확히 {numba, mlx}이고 NumPy가 없으며 모든 manifest 필드가 직렬화되는지 검사한다.
  5. 음수 reference tolerance가 Python 기준 STOP을 일으키고, 잘못된 repetitions·speedup·입력은 거부되는지 검사한다.
  6. 실제 MLX가 가능한 환경에서는 실제 smoke를 실행한다. 적격이면 모든 gate와 speedup을 만족해야 하고, 부적격이면 비어 있지 않은 fallback reason이 있어야 한다.
  7. 같은 입력 assessment 두 번의 계산 결과·gate 결과는 같게 검사하되 wall-clock timing 숫자 자체의 byte 동일성은 요구하지 않는다.
