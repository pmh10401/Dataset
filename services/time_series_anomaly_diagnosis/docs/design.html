승인된 제품 설계

시계열 이상 진단 서비스

연구팀이 데이터베이스의 데이터셋을 선택하고, 이상 탐지 결과와 검토 후보를 그래프로 확인하는 내부 서비스입니다.

사용자: 연구팀 현재 검증 모델 유지 공용 순차 대기열 결과 영구 저장 사용 안내서

진행 상태

1. 목표와 성공 기준

사용자는 파일 경로나 실험 번호를 알 필요가 없어야 합니다. 데이터셋을 고르고 분석 버튼을 누르면, 작업 상태와 결과를 한 화면에서 이해할 수 있어야 합니다.

데이터셋 선택

데이터베이스에 등록된 1,119개 데이터셋을 검색하고 선택합니다.

분석 실행

여러 연구자의 요청을 공용 대기열에 넣고 한 건씩 실행합니다.

눈으로 확인

시계열 그래프에서 자동 탐지와 표본 수 제한 경고를 함께 표시합니다.

나중에 다시 보기

분석 기록과 결과는 서버 재시작 뒤에도 남습니다.

현재 실행 범위: DB 1,119개를 모두 목록에 표시합니다. 검증된 경로가 있는 1,117개 중 일반 경로 801개와 Numba 복구 경로 155개, 총 956개를 실행할 수 있습니다. 학습 시계열이 5개 미만인 161개와 검증된 라우팅이 없는 2개는 이유와 함께 실행 불가로 표시합니다.

7. 분석 데이터 흐름

  1. 웹 화면이 GET /api/datasets로 DB의 1,119개 데이터셋과 실행 가능 여부를 읽습니다.
  2. 사용자가 분석을 요청하면 POST /api/analysis-runs가 요청을 검증하고 대기 중 기록을 저장합니다.
  3. 공용 작업자가 원본 DB에서 학습·평가 시계열을 읽습니다.
  4. 정상 클래스는 원본 데이터셋의 최빈 클래스를 기준으로 미리 만든 DB 라벨을 그대로 사용합니다. 서비스가 특정 숫자를 정상이라고 새로 판단하지 않습니다.
  5. 저장된 라우팅과 검증 모델로 점수와 자동 이상 후보를 계산합니다. 데이터셋 이름은 저장된 자료를 찾는 키일 뿐, 라우팅 특징으로 사용하지 않습니다.
  6. 정답 라벨을 보지 않고 동결된 다중 증거로 P1·P2·P3 검토 후보를 만듭니다.
  7. 자동 탐지에 이미 포함된 시계열은 검토 후보에서 빼고 자동 탐지 쪽에 한 번만 표시합니다.
  8. 후보가 모두 정해진 뒤에만 정답 라벨로 AUC·FN·FP를 계산합니다.
  9. 결과를 서비스 DB에 저장하고 웹 화면이 그래프와 표로 표시합니다.

8. 다중 증거 검토 규칙

P1 — 서로 다른 증거군 2개 이상
가장 먼저 검토
P2 — 증거군 1개
P1 다음에 검토
P3 — 증거군 0개
기본 화면에서는 접어서 표시

증거군은 통계, 구조, 변화점, 가림 복원, 공식 변환 모델의 다섯 종류입니다. 같은 종류 안의 여러 변형은 먼저 하나의 표로 합쳐 중복 표를 막습니다.

검증된 라우팅 1,117개 중 1,116개는 동결된 증거와 정확히 연결됩니다. 라우팅은 있지만 증거가 없는 1개는 다른 이름으로 억지 연결하지 않고 “자동 탐지만 제공”이라고 표시합니다. 증거는 있지만 라우팅이 없는 항목도 실행 가능한 다른 데이터셋으로 바꾸어 연결하지 않습니다.

자동 승격을 하지 않는 이유: 기존 검증에서 가장 강한 P1 후보도 일부가 오탐이었습니다. 따라서 높은 우선순위는 “먼저 확인할 가치”를 뜻하며 “확정 이상”을 뜻하지 않습니다.

10. 저장과 재시작

서비스 DB는 단순한 analysis_runs 표 하나로 시작합니다. 요청 정보, 상태, 시간, 오류 메시지, 사용 모델, 결과 JSON을 저장합니다.

  • 완료된 결과는 재시작 뒤에도 그대로 엽니다.
  • 서버가 꺼질 때 실행 중이거나 대기 중이던 작업은 시작 시 중단됨으로 바꾸고 다시 실행 버튼을 제공합니다.
  • 원본 데이터 DB에는 쓰지 않습니다.

11. 오류 처리

학습 자료나 모델 자료 부족분석 전에 실행 불가 이유를 표시

12. 성능 가속 판단

이번 작업은 검증된 점수 계산 방식을 바꾸지 않습니다. 새로 추가되는 대기열·SQLite·후보 정렬은 작은 작업이므로 별도의 가속 코드를 만들지 않습니다.

  • 새로운 대규모 NumPy 점수 계산 단계는 만들지 않습니다.
  • 기존 점수 계산을 옮길 때 결과와 후보가 완전히 같은지 먼저 확인합니다.
  • 실제 병목이 측정될 때만 Numba를 비교하며, 컴파일 시간을 포함해 더 빠르고 결과가 같을 때만 사용합니다.
  • 새 점수 모델이 아니므로 이번 서비스 구축에서 MLX 경로는 추가하지 않습니다.

13. 검증 계획

  1. 목록 검증: DB 1,119개, 검증된 라우팅 1,117개, 실행 가능 956개, 소표본 보류 161개, 라우팅 없음 2개가 정확히 표시되는지 확인합니다.
  2. 모델 일치: 각 라우팅 방법의 대표 데이터셋에서 유한한 점수가 생성되고, 결과 행 수가 평가 인덱스 수와 같으며, AUC가 저장된 기대값과 같은지 확인합니다.
  3. 증거 경계: 1,116개 연결, 증거 없는 1개, 모든 후보 인덱스 범위를 확인합니다.
  4. 라벨 누출 방지: P1·P2·P3를 만든 뒤에만 정답 라벨을 읽는지 테스트합니다.
  5. 기록 검증: 완료·실패·중단 상태가 저장되고 재시작 뒤 복구되는지 확인합니다.
  6. 브라우저 E2E: 데이터셋 선택부터 그래프와 후보 확인까지 실제 화면에서 실행합니다.

서비스 통합 검증을 위해 모든 점수를 다시 계산하지는 않습니다. 이미 검증된 모델은 대표 데이터셋의 유한한 점수·결과 행 수·AUC 일치로 보호하고, DB 전체 1,119개에는 목록·자료 연결·실행 가능 여부 검사를 적용합니다.
