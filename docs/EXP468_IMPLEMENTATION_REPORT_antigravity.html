Exp468 구현 보고서

기술 요약

현재 구현 상태는 implementation_task_3_complete_numpy_fallback_authorized다. S10의 고정 STFT·자연로그 JS·LOO·rank·confirmation 수식과 Numba parity를 검증했다. clean subprocess에서 backend 준비부터 포함한 Numba 결과는 NumPy 대비 0.05559174383559552x라서 필수 1.1x를 통과하지 못했고, MLX/MPS도 GPU float64 RFFT를 지원하지 않는다. 사용자는 2026-08-24에 NumPy CPU 예외를 승인했다. 따라서 gate_passed=false, fallback_authorized=true, selected_backend=numpy를 서로 다른 사실로 보존하고 Task 3을 완료했다. 다음 작업은 Task 4이며 공식·private qualification은 실행하지 않았다.

Task 1 완료 범위

  • config_antigravity.py는 TRAIN-only identity, seed/fold, 5×28 창, 대칭 Hann 수학 기준, RFFT·epsilon·자연로그 JS, 네 변화 순서, C0/S10/C10 역할, period 기준과 설계 SHA-256을 exact-type frozen dataclass로 고정한다.
  • contracts_antigravity.py는 fold와 qualification 형식을 불변으로 제공한다. 두 AUC tuple은 config의 네 변화 순서에 묶이며 exact finite float와 [0,1] 범위만 허용한다.
  • qualification은 seed-major 10개 fold, seed 순서의 immutable count mapping, seed당 정상 trial 69개, label query 0, 실행 전 artifact hash null을 강제한다.
  • Task 1은 passed/reason 일치와 타입·범위·순서·불변성만 검사한다. period 합격과 보호 변화 기준의 실제 계산은 Task 4에 남겼다.

Task 3 완료 범위와 승인 예외

  • local_stft_antigravity.py는 exact float64 width 140에서 suffix [56:140], 시작점 (0,14,28,42,56), 길이 28의 완전한 다섯 창만 사용한다.
  • 각 창은 평균 제거, 대칭 Hann 0.5-0.5*cos(2*pi*n/27), 길이-28 RFFT, DC 제외·Nyquist 포함 14 bin, bin당 1e-12, frame L1 정규화를 적용한다. 직접 DFT fixture가 NumPy oracle과 atol=1e-15로 일치한다.
  • fit raw는 각 행을 제외한 frame별 성분 중앙값 reference, query raw는 전체 fit reference를 사용한다. reference는 frame별 합 1로 재정규화한다. query를 fit에 섞는 leakage fixture와 duplicate/tied median fixture를 통과한다.
  • 자연로그 Jensen–Shannon의 다섯 frame 중앙값을 raw S10으로 사용한다. rank는 (1+count(fit_raw<=query_raw))/(n_fit+1), confirmation은 raw가 0과 fit 최댓값을 모두 엄격히 넘을 때만 true다.
  • 승인 수식에 없는 수치 clamp는 없다. 1.999998644061338e-20의 작은 양의 JS와 raw가 0으로 바뀌지 않고 strict confirmation의 raw>0 의미를 보존하는 회귀 검사를 통과한다.
  • 결과 배열은 finite exact float64/bool, shape, 최대값과 backend를 검증하고 소유 복사본을 read-only로 보존한다.

전체 10-fold 가속 결과

ECG200 TRAIN 정상 69행만 사용했다. 두 seed 각각 query 크기 (14,14,14,14,13), fit 크기 (55,55,55,55,56)이며, normal과 네 합성 query를 fold별 combined batch 한 번으로 점수화해 fit calibration을 공유했다. 전체 workload는 fit raw 552개, query raw 690개, 변환 행 1,242개, 길이-28 frame 6,210개다. 데이터 load·보간·합성·조립은 timing 밖이고 backend 준비·host 반환은 timing 안이다.

NumPy와 Numba는 각각 전체 workload 21회를 순차 실행했다. raw workload 조립 뒤 clean child process를 시작하고, acceleration module·Numba import와 Hann/twiddle 생성 직전에 timer를 시작했다. 기록한 gate 0.5741005414s는 backend 준비 0.1001899168s, cold compile 0.4413024997s, warm 전체 실행 0.0326081249s를 모두 포함한다. child는 acceleration module이 timer 전에 preload되지 않았음을 검증한다. 초기 profile 개선은 유지했으며 수식·workload는 바꾸지 않았다.

NumPy fallback 승인과 불변 선택 계약

승인 문서는 docs/superpowers/specs/2026-08-24-exp468-numpy-fallback-antigravity-design-amendment.html이며 SHA-256은 benchmark artifact의 fallback_authorization.approval_document_sha256에 기록한다. 승인 전 benchmark 전체 바이트 SHA-256 938d83b0319346270a6cc32b7b6ba3efb88122dc1bf431863d8030f4539fb63b도 함께 보존한다.

backend_selection_antigravity.py는 기존 AccelerationAssessmentAntigravity를 수정하지 않고 별도의 frozen decision을 만든다. 가속 성공을 주장하려면 선택 backend가 NumPy가 아니고 eligible, parity_passed, deterministic, speedup>=1.1을 모두 만족해야 한다. 실패 fallback은 모든 non-NumPy 후보의 비어 있지 않은 실패 이유와 64자리 lowercase 승인 SHA-256을 요구한다. 승인 없이 실패 assessment를 Task 4용으로 확정하면 PermissionError가 발생한다.

왜 Numba 또는 MPS 추가 최적화로 통과할 수 없는가

NumPy 기준 31.915ms에서 1.1배 빨라지려면 후보의 준비·컴파일·계산·반환 전체가 29.014ms 이하여야 한다. 그러나 Numba는 실제 계산과 컴파일을 시작하기 전 backend 준비만 100.190ms이며, warm 전체 실행도 32.608ms다. 따라서 준비 뒤 계산 시간이 0초라고 가정해도 이 gate를 통과할 수 없다.

Apple GPU와 현재 MLX/MPS runtime은 고정 수식에 필요한 float64/complex128 RFFT를 지원하지 않는다. float32 경로는 raw atol=1e-12를 보존할 수 없으며, GPU 초기화·전송 시간도 길이 28의 작은 frame 6,210개에서 회수되지 않는다. 이 결론을 뒤집으려면 동일 clean-process workload에서 모든 준비·전송·동기화를 포함한 총시간 29.014ms 이하, raw 오차 ≤1e-12, exact rank/confirmation, 반복 결정성을 동시에 새로 증명해야 한다.

승인 반영: 과학 수식과 결과 검증, gate와 허용오차를 그대로 유지하고 현재 가장 빠른 적격 경로인 NumPy CPU로 Task 4의 성능 평가를 진행한다. 이는 Numba 또는 MLX가 가속 gate를 통과했다는 뜻이 아니다.

Task 2 완료 범위

  • sources_antigravity.py, interpolation_antigravity.py, synthetic_antigravity.py, predecessor_antigravity.py는 Exp466의 다섯 공개 함수를 직접 import하고 같은 객체로 re-export한다.
  • 승인 TRAIN의 MD5 808875aeac1c358a90c630fe369327c4와 정상 69×96 경계를 실제 loader로 확인했다. TEST 이름은 파일 열기 전에 거부되며 TEST 데이터·라벨·실제 FN은 열지 않았다.
  • 승인 TRAIN을 96→140으로 보간한 고정 1-fold fixture에서 C0 정상 배열과 level_shift, gradual_drift, amplitude_scaling, period_change 배열의 dtype·shape·bytes가 Exp466과 같음을 확인한다.
  • 새 loading, interpolation, synthetic 또는 scoring 로직은 추가하지 않았다. 실제 score 계산은 focused parity test 범위에만 한정했다.

제한·robustness·다음 단계

  • Task 3과 Step 5는 승인 fallback 예외의 감사 연결을 완료했기 때문에 체크한다. 가속 gate 자체는 계속 실패 상태다.
  • 선택 backend는 numpy이며 이는 gate 합격이 아니라 사용자가 명시적으로 승인한 CPU fallback이다.
  • 다음 단계는 threshold를 낮추거나 cold compile을 timing에서 빼는 것이 아니라 Task 4의 고정 C0/S10/C10 구현과 성능 평가다.
  • 열린 질문은 cold-start gate를 유지한 별도 사전등록 실험에서 AOT 또는 이미 컴파일된 dense transform이 정당화될 수 있는지다. Exp468의 고정 기준은 바꾸지 않는다.
