Exp449 two-root official lifecycle correction

Design status: approved correction design. Scope: documentation of the prospective lifecycle only. This document does not implement a command, execute an official command, alter an audit, or authorize a run.

Purpose: make the Exp449 predict → evaluate → inspect lifecycle structurally possible and safe. The previous single-root topology is invalid because a completed predict phase necessarily occupies the root that evaluate had to require absent. This correction separates immutable prediction authority from final evaluation publication.

1. Decision and rejected alternatives

The approved design has two distinct filesystem roots. Predict owns an immutable prediction-authority root. Evaluate reads that root by descriptor and owns a separate evaluation-publication root. Inspect reads both roots by descriptor. This is the smallest change that removes the impossible absent-root precondition while preserving an exact, inspectable prediction authority.

OptionDispositionReason
Two-root lifecycleSelectedSeparates authority from publication, keeps predict evidence immutable, and lets evaluate require a genuinely absent destination.
Single-root atomic transitionRejectedIt requires a complex transition from partial prediction evidence to evaluation publication, creating destructive-risk and making interruption recovery harder to prove.
Stop Task7RejectedIt does not meet the user goal of a safe predict → evaluate → inspect lifecycle with Task7 inspection and authenticated read-only dashboard verification.

Readiness success leaves both roots and the audit absent and non-symlink at entry and exit. A nonzero readiness outcome permanently stops Exp449: both roots remain absent and non-symlink, and the fixed audit is created only to record phase=readiness, no publication destination, the primary error, cleanup notes, and permanent-stop state. If audit writing fails, it does not mask the primary error and does not permit retry. Readiness also requires a clean reviewed commit first and last, standard-library-only work before any external capture, and zero label-capable imports before the approved evaluation label session.

Symlinks are never accepted as substitutes for absent, owned, or immutable paths. Every root check resolves the path identity without following a link into a different namespace. The fixed audit is an audit object, not a root-state repair mechanism.

3. Lifecycle and data flow

  1. Readiness: verify the clean reviewed commit, absent/non-symlink state of both roots and the audit, standard-library-only pre-capture state, and the disallowed-import boundary. On success it leaves all three paths absent and non-symlink. On nonzero outcome it permanently stops Exp449, leaves both roots absent and non-symlink, and create-only records the readiness failure in the fixed audit without masking the primary error. It performs no prediction, evaluation, label access, dashboard access, or publication.
  2. Predict: create only the prediction authority root. Run the frozen Task5 prediction procedure with label access equal to zero, produce and freeze exactly 96 candidates, and retain its immutable authority evidence. The bootstrap remains PCG64(44920260812), with 20,000 × 48 draws and SHA-256 264c780d7e5949994f1de3053158ea20a7cc3d0ae858f29770d9849b18ad4d6a. The exact worker budget is 11 workers from 12−1, with n_jobs=1; no package installation occurs.
  3. Evaluate: descriptor-capture the immutable prediction authority root before any evaluation work. Require the evaluation publication root to be absent and non-symlink. Open the sole exact label session of 48 queries and 72,300 rows, evaluate against the captured exact 96-candidate authority, and publish exactly 12 final leaves only under the evaluation root. It never changes any byte in the prediction root.
  4. Inspect: a bare inspect descriptor-captures both roots and replays evaluation semantics against the exact prediction authority. It imports no SQLite module, source module, evaluator module, aeon module, network module, or dashboard module. Inspect is permitted only after complete evaluate success.

The data flow is one-way: frozen Task5 prediction evidence → immutable descriptor capture → sole label session and Task6 computation → 12-leaf evaluation publication → descriptor-only semantic replay. The reverse direction is prohibited: labels, evaluation values, dashboard information, and inspection may not alter candidate authority.

4. Failure handling and audit truth

Any nonzero official phase command permanently stops Exp449. There is no retry, resume, override, rerun, root reuse, or recovery command. A stopped experiment remains stopped even when a subsequent condition appears repairable.

The audit writer is secondary error handling. If audit creation or serialization fails, it reports that secondary failure without masking, replacing, or reclassifying the primary phase failure; it never permits retry, resume, override, rerun, root reuse, or recovery.

5. Descriptor and namespace invariants

  • A descriptor binds a root’s canonical identity, expected role, and immutable-content identity before the dependent phase consumes it.
  • Evaluate’s prediction descriptor is captured before it opens the sole label session. Its destination descriptor is the evaluation root and must describe an absent, non-symlink namespace until publication begins.
  • Inspect captures descriptors for both completed roots before semantic replay. Its import boundary prevents it from acquiring labels or re-evaluating through SQLite, source, evaluator, aeon, network, or dashboard code.
  • Only a complete evaluate success may designate the evaluation root as final Task6 publication, and that publication has exactly 12 leaves.
  • Prediction-root identity and bytes are invariant across every evaluate and inspect outcome. Evaluation-root identity, once created, identifies either final complete publication or forensic evidence; it is never reused.
  • There is exactly one label-capable session: the evaluation session with exactly 48 queries and 72,300 rows. Predict and inspect have no label-capable imports or access.

7. Governance and hash migration

The implementation history is ordered and non-self-referential:

  1. Correction design commit: this design document.
  2. Governance/hash rebind commit: rebind the affected governance and hash contracts to the corrected lifecycle.
  3. Functional source/tests/launcher commit: implement two-root behavior through test-driven work.
  4. Truth/report/ledgers commit: record the functional candidate without self-reference.
  5. Final map-only child: update only the code map, bound to the clean truth/report/ledgers parent.

The official reviewed commit is the final clean map-only child. Readiness validates the lock-parent convention—namely that the map lock names its clean truth parent—rather than requiring the lock to equal HEAD. This prevents a generated map child from creating a self-referential governance requirement. Every listed commit must be clean at the indicated boundary.

8. Implementation task decomposition

  1. Governance and hash rebind: define the two exact roots, create-only audit phase/destination/recovery/primary-error/cleanup fields, successful-readiness absence checks, readiness-failure permanent-stop semantics, descriptor contracts, and the lock-parent validation rule.
  2. Predict contract: add failing and passing tests for absent/non-symlink entry, zero label access, exact bootstrap, 11-worker constraint, immutable 96-candidate Task5 authority, and preserved partial failure evidence.
  3. Evaluate contract: add failing and passing tests for prediction descriptor capture, absent/non-symlink evaluation destination, sole 48-query/72,300-row label session, byte-invariant prediction root, exact 12-leaf publication, and forensic evaluation failures.
  4. Inspect contract: add failing and passing tests for both descriptors, complete-evaluation gate, semantic replay, and the prohibited-import boundary.
  5. Task7 evidence contract: add tests and reporting rules for authenticated read-only dashboard verification and explicitly blocked unavailable access, using only local synthetic Exp449 payload.
  6. Truth, reports, ledgers, and map: record the functional candidate without self-reference, then generate the final map-only child whose lock identifies its clean truth parent.
