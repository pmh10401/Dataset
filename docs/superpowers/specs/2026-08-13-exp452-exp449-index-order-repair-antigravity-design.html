Exp452: Exp449 인덱스 순서 복구 설계

한 줄 요약: Exp449의 후보 결과는 맞았지만, 같은 숫자 목록을 서로 다른 순서로 저장해서 최종 검사가 실패했다. Exp452는 숫자를 항상 작은 값부터 정렬해 저장하는 한 가지 문제만 고친다.

현재 상태
  • Exp449 prediction은 48개 데이터셋, 96개 후보를 만들었고 TEST label을 읽지 않았다.
  • Prediction aggregate SHA-256은 a6054a44fc4e78f354dcf61d2e003284804680cd4197405364fcb5ef8d822e0d이다.
  • Exp449 evaluation은 TEST label session 1회, 48개 query, 72,300개 row를 읽었다.
  • 최종 공개 전 검사에서 frozen prediction indices differ from evidence 오류가 발생했다.
  • Exp449는 영구 중단됐다. 재실행, inspect, artifact 수정, dashboard 게시를 하지 않는다.

1. 무엇이 잘못됐는가?

index는 이상으로 판단된 데이터 위치 번호다. 예를 들어 [2, 5, 9]는 2번, 5번, 9번 위치를 골랐다는 뜻이다.

Exp449에서 prediction은 index를 작은 값부터 정렬해서 저장했다. 그러나 evaluation은 같은 index를 frozenset이라는 순서 없는 상자에 넣었다가 바로 list로 바꾸었다. 이 과정에서 숫자 순서가 달라졌다.

자료저장된 값
Prediction[981, 983, 984, 986, 988, 989, 992, 993, 994, 995, 996, 998, 999]
Evaluation evidence[992, 993, 994, 995, 996, 998, 999, 981, 983, 984, 986, 988, 989]

두 목록에 들어 있는 숫자는 완전히 같다. 순서만 다르다. 전체 96개 후보 중 75개에서 이 문제가 나타났고, 75개 모두 두 목록의 숫자 집합은 정확히 같았다. 따라서 후보 계산이나 confusion 값이 달라진 문제가 아니라 저장 순서 문제다.

2. 선택한 해결 방법

Exp452 evaluation은 evidence를 만들 때 아래 규칙을 사용한다.

indices = sorted(indices)

즉, index를 항상 작은 숫자부터 저장한다. Replay는 기존처럼 두 list가 순서까지 정확히 같은지 검사한다. 검사를 느슨하게 만들지 않는다.

4. Exp449 결과를 어떻게 다루는가?

Exp449 staging에는 qualified candidate 2개가 기록되어 있다. 하지만 최종 replay가 실패했으므로 공식 결과가 아니다. Exp452의 후보 선택, threshold 변경, 방법 제거, routing 규칙 설계에 이 숫자를 사용하지 않는다.

Exp452는 Exp449에서 이미 고정한 96개 prediction을 모두 그대로 평가한다. 결과를 본 뒤 같은 실험 안에서 설정을 바꾸지 않는다.

6. 테스트 순서

  1. RED: 같은 index 집합을 서로 다른 순서로 넣었을 때 기존 방식이 replay에서 실패하는지 확인한다.
  2. GREEN: evidence 저장 전에 정렬하면 두 list가 정확히 같아지는지 확인한다.
  3. 96개 synthetic 후보 전체에서 prediction list와 evidence list가 순서까지 같은지 확인한다.
  4. index가 빠지거나 추가되거나 중복되면 반드시 실패하는지 확인한다.
  5. 후보, seed, alpha, threshold, bootstrap, confusion 계산이 Exp449와 같다는 differential test를 실행한다.
  6. 실제 TEST label을 읽지 않는 회귀 테스트를 두 번 실행한다.
  7. fresh Terra 구현 검토와 fresh Sol 최종 검토를 통과한다.

7. 공식 실행 규칙

구현과 검토가 끝난 뒤에만 Exp452 official lifecycle을 한 번 실행할 수 있다. 명령은 readiness --reviewed-commit LOWER40HEX, evaluate --reviewed-commit LOWER40HEX, bare inspect 순서로 각각 한 번만 허용한다. Exp449 prediction을 새로 만들지 않으므로 Exp452에는 별도 predict command를 두지 않는다.

readiness와 evaluate는 fresh Sol이 승인한 동일한 clean commit을 받아야 한다. inspect는 argument를 받지 않으며, evaluation artifact와 receipt 안의 reviewed commit이 그 동일한 commit인지 확인한다. HEAD, map lock, receipt, artifact 중 하나라도 다른 commit을 가리키면 실패한다.

  • Readiness가 실패하면 evaluate와 inspect를 실행하지 않는다.
  • Evaluate가 실패하면 inspect를 실행하지 않는다.
  • 성공한 immutable evaluation root가 있을 때만 inspect를 한 번 실행한다.
  • 실패하면 재시도하지 않고 새 실험 번호를 사용한다.

8. CPU·MLX·MPS 가속 판단

Exp452가 새로 하는 계산은 96개의 짧은 Python 정수 목록을 정렬하는 일이다. 새 score를 만들거나 큰 행렬을 계산하지 않는다. 이 작업을 GPU tensor로 바꾸면 Python list와 정확히 같은 정수 순서를 만드는 별도 변환이 필요하고, 장치로 데이터를 보내고 다시 가져오는 시간이 더 든다. 따라서 frozen 알고리즘을 그대로 유지하면서 빨라질 수 있는 tensor 단계가 아니다.

  • Tensor 사용 가능성: 없음. 변경 대상은 canonical JSON에 넣을 Python 정수 list다.
  • Backend 확인: readiness는 PyTorch, MLX, mlx-metal, MPS 사용 가능 여부와 버전을 기록한다.
  • 같은 결과 확인: synthetic test에서 CPU 정렬 결과가 frozen prediction list와 정확히 같은지 확인한다.
  • 속도 기준: 실제 tensor 대상이 없으므로 MLX/MPS benchmark를 공식 평가에 넣지 않는다. 향후 tensor 단계가 생기면 전송·동기화 시간을 포함해 CPU보다 최소 1.1배 빠르고 index가 모두 같을 때만 사용한다.
  • 결론: Exp452는 CPU 단일 프로세스를 사용한다. MLX/MPS 미사용 이유를 manifest에 기록한다.

9. 성공 기준

  • 96개 prediction indices와 evaluation evidence indices가 순서까지 정확히 같다.
  • 48개 query와 72,300개 label row 수가 정확하다.
  • 12개 evaluation leaf와 artifact SHA map이 source-free replay를 통과한다.
  • 기존 FN·FP·F1 기준을 그대로 적용한다.
  • 자동 routing, champion 변경, promotion은 하지 않는다.
Dashboard 규칙: Exp452 evaluation과 source-free inspect가 모두 성공하고 truth closeout 검토까지 끝난 경우에만 aggregate 결과를 dashboard에 게시할 수 있다. Raw label, index 목록, 데이터셋별 상세 row, local path, hash, log는 게시하지 않는다. 실패 결과나 staging 결과는 게시하지 않는다.

10. 구현 단계

  1. Exp452 governance HTML, preregistration, runbook, implementation report, code map을 만든다.
  2. Exp449 실패 audit·prediction·staging을 읽기 전용으로 검증하는 predecessor gate를 만든다.
  3. Exp449 evaluator/replay를 controlled fork하고, index 정렬 한 곳만 의미 있게 변경한다.
  4. Closed CLI와 launcher를 만들고 전체 회귀 검증을 수행한다.
  5. fresh Terra와 fresh Sol이 exact clean commit을 검토한다.
  6. 사용자 승인 후 official lifecycle을 한 번 실행한다.

11. 설계 결론

Exp452는 새 방법을 시험하는 실험이 아니다. Exp449에서 이미 고정한 후보를 바꾸지 않고, 같은 숫자 목록을 항상 같은 순서로 적도록 고치는 공학적 복구 실험이다. 이 작은 경계를 지켜야 Exp449의 TEST 결과를 이용한 사후 튜닝을 막을 수 있다.
